# 3강: 큐 (Queue)

## 실행

```bash
cd lessons/03-queue
make run
```

약 2초 뒤 스스로 종료한다.

## 배우는 것

- 큐는 데이터를 **복사**한다 — 그래서 지역 변수를 보내도 안전하다
- 소비자는 데이터가 올 때까지 **CPU를 전혀 쓰지 않고** 기다린다
- 큐가 가득 찰 때 어떻게 할지가 **설계 결정**이다
- 큐는 속도 차이를 **흡수**할 뿐 **해결**하지 못한다

## 왜 전역 변수가 아니라 큐인가

```c
typedef struct { int x, y; } Point_t;
Point_t g_pos;              /* 전역 공유 */

g_pos.x = 10;
        /* ← 여기서 선점당하면 */
g_pos.y = 20;
```

읽는 쪽이 `x=10, y=이전값`을 보게 된다. **한 번도 존재한 적 없는 상태**다.
찢어진 읽기(torn read)라고 하고, 재현이 거의 안 되는 버그의 전형이다.

큐는 구조체를 **통째로** 복사하므로 이런 중간 상태가 노출되지 않는다.

## 실습 1 — 큐는 값을 복사한다

```c
xOut.sValue = 25;
xQueueSend(xQueue, &xOut, 0);

xOut.sValue = 999;          /* 보낸 뒤 원본을 훼손 */

xQueueReceive(xQueue, &xIn, 0);
/* xIn.sValue 는? */
```

### 실행 결과

```
  보내기 전   : sValue = 25
  보낸 뒤 원본을 999로 덮어씀
  받은 값     : sValue = 25
```

`&xOut`은 **"여기서 읽어가라"**는 뜻이지 포인터를 넘겨 공유하는 게 아니다.
커널이 `memcpy`로 큐 내부 버퍼에 복사한다
([kernel/queue.c](../../kernel/queue.c)의 `prvCopyDataToQueue`).

**그래서 보낼 데이터는 지역 변수여도 안전하다.** 보낸 직후 스코프를 벗어나도
상관없다. 이것이 큐를 "확신이 안 서면 이걸 쓰라"고 말할 수 있게 하는 성질이다.

## 실습 2 — 생산자·소비자

생산 150ms 주기, 소비자는 `portMAX_DELAY`로 무한 대기.

### 실행 결과

```
[   152 ms][Prod     ] 생산 #1 (값 23) -> 큐에 넣음
[   152 ms][Cons     ]   소비 #1 (값 23) <- 큐에서 대기한 시간 0 ms
[   302 ms][Prod     ] 생산 #2 (값 26) -> 큐에 넣음
[   302 ms][Cons     ]   소비 #2 (값 26) <- 큐에서 대기한 시간 0 ms
```

**생산과 소비가 같은 시각(152ms)에 찍힌다.** 큐에서 머문 시간이 0ms다.

소비자는 그동안 `Blocked` 상태로 CPU를 전혀 쓰지 않았고, 데이터가 들어오는
순간 커널이 깨웠다. 소비자 우선순위(3)가 생산자(2)보다 높아서 **즉시 선점**해
처리했다.

폴링과 비교하면 차이가 분명하다.

```c
/* ❌ 폴링: 149ms 동안 CPU를 100% 태운다 */
while (uxQueueMessagesWaiting(q) == 0) { }

/* ✅ 블로킹: 149ms 동안 CPU 0% */
xQueueReceive(q, &x, portMAX_DELAY);
```

> **왜 소비자를 더 높은 우선순위로 두는가?**
> 큐를 가능한 한 비워두기 위해서다. 소비자가 낮으면 데이터가 큐에 쌓이고,
> 그만큼 지연이 늘고 큐가 넘칠 위험이 커진다. 과제 1에서 직접 확인한다.

## 실습 3 — 생산이 소비보다 빠르면

생산 40ms 주기, 소비 150ms 주기, 큐 길이 5.

### 실행 결과

```
[   843 ms][Cons     ]   소비 #1  [큐 0/5]
[   843 ms][Prod     ] 생산 #1   [큐 0/5]
[   883 ms][Prod     ] 생산 #2   [큐 1/5]
[   923 ms][Prod     ] 생산 #3   [큐 2/5]
[   963 ms][Prod     ] 생산 #4   [큐 3/5]
[   993 ms][Cons     ]   소비 #2  [큐 2/5]
[  1003 ms][Prod     ] 생산 #5   [큐 3/5]
[  1043 ms][Prod     ] 생산 #6   [큐 4/5]
[  1083 ms][Prod     ] 생산 #7   [큐 5/5]
[  1123 ms][Prod     ] 생산 #8   [큐 5/5]  <- 가득 참, 버림!
...
  생산 22 건, 소비 6 건, 버림 11 건
```

### 읽는 법

**① 첫 두 줄의 순서가 뒤집혀 보인다.**

```
[   843 ms][Cons     ]   소비 #1     ← 먼저 찍힘
[   843 ms][Prod     ] 생산 #1       ← 나중에 찍힘
```

생산자 코드는 이 순서다.

```c
xQueueSend(xQueue, &xSample, 0);   /* ① 보냄 */
LOG("생산 #%lu ...");              /* ② 그리고 로그 */
```

①에서 데이터가 들어가는 **순간** 소비자(우선순위 3)가 깨어나 생산자(2)를
**선점**한다. 소비자가 자기 로그를 찍고 다시 잠든 뒤에야 생산자가 ②를 실행한다.

**선점이 C 문장 사이에서 일어난다**는 것을 눈으로 보는 사례다.

**② 큐가 차오르는 속도를 계산으로 맞춰볼 수 있다.**

소비자는 150ms마다 1개를 빼고, 생산자는 40ms마다 1개를 넣는다.

```
150ms 동안 생산 ≈ 3.75개, 소비 1개  →  주기마다 약 2.75개씩 누적
큐 5칸  →  약 2주기(300ms) 만에 가득 참
```

실제로 843ms에 시작해 1123ms(약 280ms 뒤)에 첫 버림이 발생했다.

**③ 숫자가 맞아떨어진다.**

```
생산 22 = 소비 6 + 버림 11 + 큐에 남은 5
```

**④ 큐는 해결책이 아니다.**

큐를 100칸으로 늘리면? 넘치는 시점이 늦춰질 뿐 **결국 넘친다**.
평균 생산 속도가 평균 소비 속도보다 빠르면 어떤 크기의 버퍼도 부족하다.

큐가 유용한 것은 **순간적인 폭주(burst)를 흡수**할 때다.
평균적으로는 소비가 생산을 따라잡을 수 있어야 한다.

## 큐가 찼을 때 — 타임아웃이 곧 설계다

```c
xQueueSend(q, &data, <타임아웃>);
```

| 타임아웃 | 동작 | 쓰는 곳 |
|---|---|---|
| `0` | 자리 없으면 즉시 포기 | **주기를 지켜야 하는 태스크.** 블로킹하면 주기가 깨진다 |
| `portMAX_DELAY` | 자리 날 때까지 무한 대기 | 데이터를 절대 잃으면 안 되고, 지연은 허용될 때 |
| `pdMS_TO_TICKS(n)` | n ms까지만 기다림 | 절충 |

이 실습은 `0`을 썼다. 생산자가 `xTaskDelayUntil`로 40ms 주기를 지켜야 하는데,
큐에서 블로킹하면 주기가 무너지기 때문이다 (2강의 마감 위반).

**반환값을 반드시 확인해야 한다.**

```c
if (xQueueSend(q, &data, 0) != pdPASS) {
    ulDropCount++;      /* 이걸 안 세면 데이터가 조용히 사라진다 */
}
```

## 자주 쓰는 API

| 함수 | 설명 |
|---|---|
| `xQueueCreate(개수, 항목크기)` | 큐 생성. 힙에서 `개수 × 크기` 확보 |
| `xQueueSend` / `xQueueSendToBack` | 뒤에 넣음 (FIFO) |
| `xQueueSendToFront` | 앞에 넣음. 긴급 메시지용 |
| `xQueueReceive` | 꺼내면서 제거 |
| `xQueuePeek` | 꺼내되 **제거하지 않음** |
| `uxQueueMessagesWaiting` | 현재 몇 개 들어있나 |
| `xQueueReset` | 비움 |
| `xQueueSendFromISR` | **ISR 전용.** 타임아웃 없음 (4강) |

## 과제

### 과제 1 — 우선순위를 뒤집는다

`PRIO_CONSUMER`를 `3`에서 `1`로 바꿔 생산자보다 낮게 만들어라.

실습 2의 "큐에서 대기한 시간"이 어떻게 변하는가? 실습 3의 버림 건수는?

> 소비자가 낮으면 데이터가 큐에 머무는 시간이 길어진다.
> 이것이 소비자를 높게 두는 이유다.

### 과제 2 — 큐 크기를 바꾼다

`QUEUE_LEN`을 `5`에서 `50`으로 늘려라. 실습 3에서 버림이 사라지는가?

그다음 실행 시간을 `prvRunPair(..., 900)`에서 `5000`으로 늘려 보라.
결론이 달라지는가?

> 버퍼 크기는 **폭주 흡수량**을 결정할 뿐, 평균 속도 불균형은 해결하지 못한다.

### 과제 3 — 타임아웃을 바꿔 본다

실습 3의 `vFastProducerTask`에서 타임아웃을 `0` → `portMAX_DELAY`로 바꿔라.

버림이 사라지는 대신 무엇이 희생되는가? 생산 시각을 보라.

> 생산자가 40ms 주기를 지키지 못하게 된다. **데이터 손실 대신 주기가 깨진다.**
> 둘 중 무엇을 포기할지가 설계 결정이다.

### 과제 4 — `xQueuePeek`을 써 본다

실습 1에서 `xQueueReceive` 대신 `xQueuePeek`을 쓴 뒤,
`uxQueueMessagesWaiting()`을 찍어 보라. 값이 어떻게 다른가?

### 과제 5 — 큐 없이 전역 변수로 바꿔 본다 (심화)
