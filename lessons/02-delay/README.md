# 2강: 딜레이와 주기 실행

## 실행

```bash
cd lessons/02-delay
make run
```

약 2초 뒤 스스로 종료한다.

## 배우는 것

- `vTaskDelay()`로 주기를 만들면 **오차가 누적된다**(드리프트)
- `xTaskDelayUntil()`은 절대 시각 기준이라 드리프트가 없다
- 작업이 주기보다 길어지면 FreeRTOS가 어떻게 동작하는가
- `xTaskDelayUntil()`의 **반환값**이 마감 위반을 감지하는 유일한 신호다

## 왜 한 태스크가 세 실습을 순서대로 하는가

여러 태스크를 동시에 돌리면 서로 CPU를 뺏어 측정값이 오염된다.
타이밍을 측정하는 것이 목적이므로 간섭을 없앴다.

## 실습 1 — `vTaskDelay()`는 밀린다

```c
for (;;) {
    do_work();                          /* 매번 시간이 다르다 */
    vTaskDelay(pdMS_TO_TICKS(100));     /* "지금부터" 100ms */
}
```

`vTaskDelay(N)`은 **호출한 시점부터** N틱이다. 따라서

```
실제 주기 = 작업 시간 + 100ms
```

작업 시간이 매번 다르면 주기도 매번 다르고, 그 오차가 쌓인다.

### 실행 결과

```
  회차 | 작업시간 | 실제 경과 | 이상적 | 누적 오차
  -----+----------+-----------+--------+----------
     1 |     10 ms |     106 ms |  100 ms |     +6 ms
     2 |     25 ms |     230 ms |  200 ms |    +30 ms
     3 |     15 ms |     342 ms |  300 ms |    +42 ms
     4 |     30 ms |     471 ms |  400 ms |    +71 ms
     5 |     12 ms |     582 ms |  500 ms |    +82 ms
     6 |     28 ms |     710 ms |  600 ms |   +110 ms
     7 |     18 ms |     827 ms |  700 ms |   +127 ms
     8 |     22 ms |     948 ms |  800 ms |   +148 ms
```

**8회 만에 148ms가 밀렸다.** 이 추세면 1000회에 18초, 하루면 수십 분이 밀린다.
매 회차 오차 증가분이 그 회차의 작업 시간과 거의 같다는 점을 확인하라.

> 1회차 오차가 작업 시간(10ms)보다 작은 6ms인 이유:
> `vTaskDelay(100)`은 "100틱 뒤"가 아니라 "현재 틱이 끝나고 100번째 틱"이라,
> 실제로는 99~100ms 사이가 된다. 틱 분해능의 한계다.

## 실습 2 — `xTaskDelayUntil()`은 고정된다

```c
TickType_t xLastWake = xTaskGetTickCount();   /* 기준점 초기화 (필수!) */

for (;;) {
    xTaskDelayUntil(&xLastWake, pdMS_TO_TICKS(100));   /* 루프 맨 앞 */
    do_work();
}
```

커널이 `xLastWake`에 마지막으로 깨운 시각을 저장하고,
**거기에 주기를 더한 절대 시각**에 다시 깨운다.

### 실행 결과

```
  회차 | 작업시간 | 깨어난 시각 | 이상적 | 누적 오차
  -----+----------+-------------+--------+----------
     1 |     10 ms |       100 ms |  100 ms |     +0 ms
     2 |     25 ms |       200 ms |  200 ms |     +0 ms
     ...
     8 |     22 ms |       800 ms |  800 ms |     +0 ms
```

**작업 시간이 10~30ms로 들쭉날쭉한데도 오차가 정확히 0이다.**
실습 1과 작업 시간 패턴이 완전히 동일하다는 점이 핵심이다.

### 주의 — `xLastWake` 초기화를 빠뜨리면

```c
TickType_t xLastWake;                       /* ❌ 쓰레기 값 */
xTaskDelayUntil(&xLastWake, ...);
```

지역 변수라 초기값이 쓰레기다. 동작이 엉망이 되고 원인 찾기도 어렵다.
반드시 `xTaskGetTickCount()`로 초기화한다.

## 실습 3 — 주기를 넘기면

주기 50ms인데 4, 5회차만 130ms 작업을 시켰다.

```
  회차 | 작업시간 | 시작 시각 | 이상적 | 마감
  -----+----------+-----------+--------+--------------
     1 |     20 ms |      50 ms |   50 ms | 준수
     2 |     20 ms |     100 ms |  100 ms | 준수
     3 |     20 ms |     150 ms |  150 ms | 준수
     4 |    130 ms |     200 ms |  200 ms | 준수
     5 |    130 ms |     328 ms |  250 ms | 위반 (대기 없이 즉시 실행)
     6 |     20 ms |     446 ms |  300 ms | 위반 (대기 없이 즉시 실행)
     7 |     20 ms |     466 ms |  350 ms | 위반 (대기 없이 즉시 실행)
     8 |     20 ms |     485 ms |  400 ms | 위반 (대기 없이 즉시 실행)
     9 |     20 ms |     505 ms |  450 ms | 위반 (대기 없이 즉시 실행)
    10 |     20 ms |     526 ms |  500 ms | 위반 (대기 없이 즉시 실행)
```

### 읽는 법

**① FreeRTOS는 마감을 강제하지 않는다.** 에러도 예외도 없다. 그냥 밀릴 뿐이다.

**② 4회차는 "준수"로 나온다.** 130ms 작업을 *시작하는* 시점은 정시(200ms)였기
때문이다. 위반이 드러나는 것은 **다음 회차**다. 마감 위반은 항상 한 박자 늦게
감지된다는 뜻이다.

**③ 6~10회차는 작업이 20ms인데도 계속 위반이다.** 5회차까지 260ms가 밀렸고,
한 회차마다 `50ms(주기) - 20ms(작업) = 30ms`씩만 회복하기 때문이다.
**한 번 크게 밀리면 회복에 여러 주기가 걸린다.**

**④ 6→7회차 간격이 20ms다.** 주기인 50ms가 아니다.
`xTaskDelayUntil()`이 대기 없이 즉시 반환해서 **쉬지 않고 연속 실행**하고 있다.
이것이 catch-up 동작이며, 이 동안 낮은 우선순위 태스크는 CPU를 거의 못 받는다.

### 마감 위반을 감지하는 법

```c
if (xTaskDelayUntil(&xLastWake, xPeriod) == pdFALSE) {
    ulDeadlineMissCount++;      /* 대기 없이 반환 = 마감 위반 */
}
```

**이 반환값이 유일한 신호다.** 확인하지 않으면 시스템은 조용히 느려질 뿐,
아무도 모른다. 옛 API `vTaskDelayUntil()`은 반환값이 없으므로
**`xTaskDelayUntil()`을 써야 하는 이유**가 바로 이것이다.

## 과제

### 과제 1 — 드리프트를 극단적으로 만들어 본다

`prvWorkMs()`가 반환하는 작업 시간을 전부 `80`으로 바꿔 보라.
(주기 100ms에 작업 80ms)

실습 1의 누적 오차가 8회차에 얼마가 되는가? 실습 2는?

### 과제 2 — 순서를 바꿔 본다

실습 2에서 `xTaskDelayUntil()`을 루프 **맨 뒤**로 옮겨 보라.

```c
for (i = 1; i <= CYCLES; i++) {
    lab_burn_ms(ulWork);
    xTaskDelayUntil(&xLastWake, pdMS_TO_TICKS(PERIOD_MS));
    /* 측정 */
}
```

결과가 달라지는가? 왜 그런가?

> 힌트: `xLastWake`는 커널이 갱신한다. 측정 시점만 바뀔 뿐 깨우는 시각의
> 기준은 변하지 않는다. 그래도 관용적으로 맨 앞에 두는 이유를 생각해 보라.

### 과제 3 — 회복 시간을 계산으로 예측한다

실습 3에서 `prvOverrunWorkMs()`의 정상 작업 시간을 `20` → `40`으로 바꾸면,
밀린 260ms를 회복하는 데 몇 회차가 걸릴까?

**먼저 계산한 뒤** 실행해서 맞춰 보라.

> 회차당 회복량 = 주기 - 작업시간

### 과제 4 — 틱 분해능을 바꿔 본다

`common/FreeRTOSConfig.h`에서 `configTICK_RATE_HZ`를 `1000`에서 `100`으로
바꾸면(1틱 = 10ms) 실습 2의 결과가 어떻게 되는가?

주기를 `PERIOD_MS 100`에서 `35`처럼 틱의 배수가 아닌 값으로 바꾸면?

> `pdMS_TO_TICKS(35)`가 몇 틱이 되는지 계산해 보라.
> 틱보다 정밀한 주기는 만들 수 없다.

**주의:** 이 파일은 모든 레슨이 공유하므로 실험 후 되돌려 놓을 것.

## 실무 정리

1. 주기 태스크는 **무조건 `xTaskDelayUntil()`**
2. `xLastWake`를 `xTaskGetTickCount()`로 **초기화**
3. **반환값을 확인해 마감 위반을 카운트**
4. 초과가 잦으면 → 원인이 간섭이면 우선순위 재설계(주기 짧을수록 높게),
   실행 시간이면 무거운 일을 낮은 우선순위 태스크로 분리 (3강)
5. CPU 사용률 **70%**를 넘기지 말 것
